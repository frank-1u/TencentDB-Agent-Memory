03 / CONFIGURATION CONTRACT

保留 MEMORY_LLM 配置组，把地址和模型指向聚合

协议层配置候选

B 的配置形态

MEMORY_LLM_BASE_URL=http://<router-host>:15721/v1
MEMORY_LLM_API_KEY=local-router-placeholder
MEMORY_LLM_MODEL=ccs-<published-key>/<real-model>
MEMORY_LLM_PROTOCOL=openai

占位值供 SDK 构造认证头；cc-Switch 在选定 API 供应商后替换为真实 Key。占位值不是厂商 API Key，也不是 Memory Core 的 sk-mem 身份。

  • Core 保持 llm.provider=openai / 默认透传；不要设置会追加 MemoryProxy 路径的 provider=proxy。
  • Knowledge 保持 LLM_MODE=custom；custom 表示使用配置地址，地址可以是 cc-Switch。检查实例 binding 是否覆盖全局值。
  • Proxy 任务草稿也使用完整的这组配置；需补齐容器环境变量注入，禁止字段缺失时回用编码上游。

cc-Switch 需要怎样配置

  1. 在 Codex 应用下添加记忆专用 API 供应商条目，确认其原生 Chat Completions endpoint 可用。可以和其他用途复用同一厂商 Key，但建议有独立条目以固定目标和观察用量。
  2. 把该条目加入 Codex 聚合、发布实际模型；从发布结果复制完整 ccs-key/model。注册 key 不是随意填写的显示名。
  3. OpenAI Official 可保留为 Codex 聚合默认；Claude 应用的 GLM 路由仍按其独立配置工作。Claude 页已有卡片不会自动成为 Codex 聚合成员。
  4. 确认聚合已生效，再验证 MemoryProxy profile / 启动参数入口。现有聚合启用流程会写客户端配置，不能同时假设“完全不接管”且“聚合已独立激活”。
地址与协议要同时匹配。Core 的 Standalone runner、local offload，以及 Knowledge 的 OpenAI 分支均使用 provider.chat(...)。统一配置应请求 /v1/chat/completions；该入口不自动执行 Responses 输入才有的协议转换。目标供应商必须原生接受 Chat，不能只因为它能在 Codex 中使用就推断兼容。
04 / BOUNDARIES

固定供应商，不等于固定所有状态

变化或输入当前源码行为设计要求
默认供应商改变，聚合仍开启且成员保留正确的完整聚合 ID 仍选原 key 对应供应商。显式绑定记忆模型，不跟随当前默认目标。
未知 key、移除 / 删除供应商、退出聚合已识别的完整聚合 ID 报错，不切默认。明确失败，不删除前缀后重试其他模型。
ccs-foo 缺少 /，或用错 app 前缀可能被当普通 model，进入默认路由。集成端在发请求前严格校验 endpoint、app、key、model 和分隔符。
供应商改显示名注册 key 保持；删除重建卡片不保证旧 key 有效。复制已发布标识，不用显示名自行拼接。
仅从发布列表删除 / 重命名模型，供应商仍在旧 ID 仍可能把旧 model 发给原供应商，由上游接受或拒绝。发布目录不是严格调用白名单；更新绑定并重新验证。
同一供应商卡片的 endpoint / Key 改变固定的是 provider ID；后续请求读取当前卡片配置。供应商配置变更也要纳入记忆模型变更记录。
只启动 HTTP 服务，没有启用该 app 聚合不会自动激活聚合 registry；完整 alias 会遇到 StackOff。现有产品需启用对应应用聚合；独立后台模式属于新能力。

三种“独立”要分开

配置独立：记忆有自己的 MEMORY_LLM 组。
目标独立：完整 alias 固定供应商和模型。
生命周期独立：当前共享 Codex 聚合开关与 cc-Switch 进程，尚未独立。

聚合不做供应商故障转移，不代表 SDK 没有请求重试。联调需要记录实际目标、模型、请求次数及错误来源。

Embedding 与订阅路径另外处理

cc-Switch 当前没有 embeddings 入口。向量化继续使用本地模型或单独的远程 Embedding 配置；JEV 等专用辅助 API 也不能按通用 Chat 接口推断支持。

第一版记忆聚合选 API Key 成员。原生 Codex Official 只能作默认且需要客户端 OAuth；Claude 页 Codex OAuth 是另一条 managed-token 路径。不能用一个本地占位值把这些机制合并成通用订阅 API。

先验证记忆聚合，再实现完整接入

顺序工作通过条件
1 · 协议与配置验证确认原生 Chat API 成员、完整注册 alias、Codex 聚合状态及实际网络地址。一个真实记忆加工调用成功，能核对供应商、真实模型、用量与结构化输出。
2 · 记忆 LLM 绑定Core / Knowledge 使用 MEMORY_LLM 聚合目标；Proxy 草稿完整注入同一组；校验 alias，缺配置不回落编码目标。抽取、摘要、L2/L3 工具往返与草稿按实际启用功能验证，输出落库可读回。
3 · 编码出口接入MemoryProxy 新增 direct / cc-Switch 模式；Codex 双凭据；保护聚合 alias，不被 main-model / model gate / instance override 改写；处理 models 与 compact。Codex 官方、Claude GLM、memory 显式 API 三类请求并发成功且不串模型或凭据。
4 · 模式与异常验证改变默认目标、切换路由/聚合、移除成员、输入坏 ID、修改发布模型；核对 profile 与客户端重写。正确 alias 保持目标或明确失败；错误格式在集成端拒绝；绝不把加工请求悄悄送默认模型。
5 · 决定是否服务化按后台可用性要求选择 A 或 B；若需不依赖 coding app 状态，再设计 D 的独立 registry 与服务入口。模式生命周期、运维责任和调用协议明确；不靠私有 DB / 状态文件维持集成。
改动范围的最终判断：记忆 Chat API 接聚合有现有配置基础，通常无需改 Core 的加工算法；整套目标仍需要 MemoryProxy 的编码接入、身份处理、模型发现与草稿配置改造。专用后台聚合 D 则需要扩展 cc-Switch。以上都尚未实施。
