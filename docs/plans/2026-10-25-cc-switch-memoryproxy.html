03 / DESIGN BOUNDARY

只设一个上游路由负责人

以下是设计约束；当前代码尚未实现全部约束。

A / CC SWITCH

保留官方供应商与路由能力

  • Codex 当前供应商选 OpenAI Official。此路径固定官方 Codex backend，校验并透传客户端 OAuth；不等同于 Claude Code 页的 Codex OAuth 预设。
  • 仅启动本地路由服务。推荐方案中 Codex 的有效入口由独立 profile 或启动参数指向 MemoryProxy，避免路由接管把客户端改回 15721、绕过记忆层。
  • 由 Codex 客户端继续管理登录与刷新。不把 OAuth access token 写进 MemoryProxy 的静态上游 API Key。
  • 官方目标保持原有禁止故障转移的行为。主推方案不引入第三方备用模型，失败时暴露错误。
B / MEMORYPROXY

增加 Codex 专用双凭据入口

  • 记忆身份：用 x-tdai-user-key: sk-mem-... 校验 Memory Core 用户，再绑定 Team / Agent / Task。
  • 模型身份：Authorization: Bearer <OAuth>、chatgpt-account-id 与会话标识保留给 CC Switch。现有 Codex 鉴权尚不读取该独立记忆头。
  • 出站剥除记忆凭据。Codex 转发当前已过滤 x-tdai-user-key，适配须复用这条边界并覆盖辅助请求。
  • 固定下一跳到 CC Switch。该部署的全局 / per-agent API Key 留空，实例上游配置不覆盖 URL、model 或鉴权，避免重新改写 OAuth 和模型。
实际改动范围优先在 MemoryProxy 增加显式、可选择的 Codex 身份提取策略；保持现有 Bearer / x-api-key 行为兼容。GitNexus 显示身份提取经 stageAuth 被 5 个 runner 共用，影响分析为 LOW、总计 7 个关联符号；实现应限定 Codex opt-in，不能直接改变所有调用方的鉴权优先级。
为什么另外两种“直接串起来”的方法不成立？

MemoryProxy → CC Switch，仍只用 sk-mem

MemoryProxy 能校验记忆用户，但 CC Switch 的 Codex OpenAI Official 路径会校验客户端传入的 OAuth。sk-mem-... 不会被自动换成该用户的 ChatGPT OAuth。

CC Switch Official → MemoryProxy

Codex OpenAI Official 的上游地址由 CC Switch 固定，普通编辑供应商 base_url 不会把这条官方路径插到 MemoryProxy。若改 CC Switch 路由层来插入记忆服务，需承担更多官方适配与请求路径耦合。

Claude Code 如何接入，并与 Codex 共用记忆？

Claude Code 可使用现有机制做另一条配置候选，不要求新增原生 Codex 的双凭据策略：记忆 Key 先交给 MemoryProxy，随后 CC Switch 用 Claude 页所选供应商的 API Key 或 managed OAuth 替换上游鉴权。此组合仍未联调。

需要为 upstream.agents.claude-code 自定义下一跳与空上游 Key，并避免实例覆盖；默认启动脚本会重写 YAML，需专用配置编排。Claude 页的 Codex OAuth 预设由 CC Switch 动态取 managed token 并转换协议，与原生 Codex 的客户端 OAuth 透传是两条路径。

04 / IMPLEMENTATION DESIGN

直接接入当前代码：新增可选的 cc-Switch 上游模式

本节为待实现设计
MODULE / CODING UPSTREAM

用一个 HTTP adapter 处理编码请求出口

在 MemoryProxy 中集中定义 coding 上游 module，让 Codex 与 Anthropic runner 通过同一 interface 取得目标 URL 和凭据策略。cc-Switch adapter 根据客户端来源选择协议入口；现有 direct adapter 保持原行为。

  • 仅配置路由服务地址；供应商 ID、GLM Key、官方 OAuth 账号与模型映射继续由 cc-Switch / 客户端管理。
  • Codex 保留客户端 OAuth；Claude 请求由 cc-Switch 替换成 GLM Key。记忆身份先在 MemoryProxy 校验。
  • 保留原生 Responses / Messages，协议转换交给 cc-Switch。v1 仅支持本提案的 Codex 与 Claude Code，其他客户端明确拒绝或维持 direct，不自动归到 Claude。
  • 两类请求分别进入对应 app_type；不读取 cc-Switch 私有 SQLite，不跨进程调用 Rust / Tauri 内部命令。
MODULE / MEMORY LLM

保留独立记忆模型，补齐 Proxy 内部调用

Core 的 llm 配置与 Knowledge 的 LLM_MODE=custom 已由 MEMORY_LLM_* 提供。本次设计保留这两条链路。

  • resolveTaskDraftConfig 虽支持 MEMORY_LLM 环境变量优先，但缺字段会回落主推理上游；不能默认认为所有记忆功能已经独立。
  • 现有 start-proxy.sh 没有将 MEMORY_LLM 组注入 Proxy 容器。cc-Switch 模式需完整注入并校验 URL / Key / Model / Protocol，避免混用两组字段。
  • 任务创建 / 更新草稿改用这组独立配置；缺配置时报明确错误，不从 Codex OAuth 或 Claude 当前模型补齐。
  • 记忆配置不因 app 供应商热切换而改变；Core 的归档、抽取和 Knowledge 资产加工继续按既有机制运行。

HTTP 接入契约中要单独处理的两点

  • 共享模型发现入口：/v1/models 会根据 anthropic-version 和 query 判定应用，并返回本地发布目录；它不是实时探测所有真实上游的接口。仅启动 router、没有对应 live 配置时，Codex 目录可能为空，需要验证专用 profile 与目录生成的配合。不要根据空目录直接判定模型调用不可用。
  • 状态与切换：HTTP /status 的 current_provider 是全局最近一次处理目标，并发时会变化。MemoryProxy 不用它选择模型；每个请求交 cc-Switch 解析该 app 的目标快照，切换仅影响该 app 后续请求。

WORKTREE / SHARED PROJECT CONTEXT

同一仓库的 worktree 复用身份与资产，不按目录迁移记忆

已有机制与建议使用方式；未实现 Orca 自动绑定。

项目共享记忆的最小约定

  • 为一个逻辑仓库固定一组 Team + 业务 Agent；主目录和各 worktree 使用同一组合。这里的业务 Agent 不等于 Codex / Claude Code 应用类型。
  • L2/L3 按 Team + Agent 共享，忽略用户、Session、Task；不同目录并不会自动建立不同记忆空间。
  • L1 召回跨 Session，但仍按 Team / User / Agent 及当前 Task 过滤。Task 按真实任务选择，不因新目录机械创建；不同 Task 不等于所有原子记忆自动互通。
  • 每个会话保留自己的 Session。需要跨任务召回 L1 时，当前接口在没有 Task 时会放宽该维度；是否使用这种方式应按真实任务语义决定。

CodeGraph 是服务端资产

  • 内置 CodeGraph 根据远端 repo_url 和登记的 branch，在 Knowledge 服务端克隆并索引；它不以客户端 cwd 作为资产 ID。
  • 相同 Team / Agent 已绑定的资产可供多个 worktree 使用，新目录无需迁移或复制索引。
  • 已注入的 match / branch 提示供模型比对工作区 git remote。它不是 Orca 自动发现或分支同步接口。
  • 未 push、未提交与未跟踪代码不会自动进入远端资产。精确编辑看当前 worktree；需要远端新快照时再 sync。
项目与用户在本方案的 Proxy 接入方式中，用户 Key 用于身份与权限；长期共享范围由 Team + Agent 决定，并非用户所有项目统一一份，也不会自动按磁盘目录分库。若两个无关仓库选择同一 Team / Agent，其长期记忆可能混在一起。建议把一个逻辑仓库映射到固定的 Team / Agent 组合。
从手选到免重复选择：只补启动时的固定身份，不建新的索引同步系统

先在各 worktree 的新会话里选择同一 Team / Agent，即可验证共享。已有 header 预选支持 x-team-id / x-agent-id / x-task-id，后续可在启动配置中固定项目身份，减少重复手选；这不等于当前已经接入了 Orca 的 worktree 生命周期。本轮 Orca CLI 桥接被未签名脚本执行策略拦截，未验证本机自动继承行为。

仓库长期经验可以共享；worktree 的未合并状态应保留分支、提交与任务语境，不能把它当成已经成立的主线事实。系统当前没有基于 worktree 的独立事实隔离保证。

推荐方案 5：Proxy 侧身份解析（双信号）

身份在服务端解析，客户端零改动。预选优先级：header 预选 > 仓库标记 > 目录绑定 > 交互表单——命中即免表单注册，未命中或校验不过回退现有表单，失败模式就是现状。

  • 接线点：stageSessionInitOrchestrate 被 claude-code / codex / workbuddy / openai-chat 四个 runner 共用，header 预选就在这里组装；追加预选来源，一处覆盖全部客户端。
  • 信号一 · 仓库标记：在业务仓库的 AGENTS.md / CLAUDE.md 提交一行 tdai-binding 标记。Claude Code 把它带进 body.system、Codex 带进 body.instructions；随 git 检出自动进入任何 worktree——Orca 建、/implement-spec 建、手动建全覆盖，无需任何登记动作。业务 ID 非凭据，公司仓库可接受。
  • 信号二 · 目录前缀：每用户「前缀 → Team/Agent」表，最长前缀匹配。覆盖不便提交标记的仓库（如外部开源仓库）与个人布局偏好；Orca 布局每仓库登记一条父目录前缀。
  • 校验复用：resolvePresetIdentity 租户校验（值必须落在用户可见 teams[] 内）；标记对不可见 Team 的用户自然失效回退表单。绑定表按用户隔离，无提权面。
  • 登记：mem:bind-project 在交互会话内输入登记，捕获客户端实际发送的 cwd 字符串，规避 WSL / 容器路径形态差异；无人在场的 subagent 会话不依赖它（靠标记信号）。

方案 5 源码证据、implement-spec 约束与对比

备选方案 2：不改 Proxy 时的客户端方案

Git 公共目录一份非凭据绑定文件，由通用包装器读取并附预选头：

{
  "team_id": "team_xxx",
  "agent_id": "agent_xxx"
}

Orca 一行脚本（拟新增命令，未创建）：

[ -x "$HOME/.local/bin/tdai-project" ] &&
  "$HOME/.local/bin/tdai-project" ensure || true

前提是 Orca 启动命令可替换为包装器且保真 app-server 协议——两点均未验证，是方案 2 的主要风险；且不经包装器启动的会话（含 /implement-spec 的 subagent）不在覆盖范围内。方案 5 落地后它退居特殊场景；header 预选保持最高优先级，两者可组合。

配置文件限制不能把“给每个 worktree 写客户端局部配置”当作两客户端的通用解法。当前 OpenAI Docs 说明 Codex 项目层会忽略 model_provider / model_providers / profiles；Claude Code 的 local settings 在部分 worktree 场景下复用主 checkout 位置。包装器应保留原启动参数、stdin/stdout 和信号，尤其不能破坏 Orca 的 app-server 协议。

2026-10-25 复评（结合两仓库源码）后，主推由方案 2 改为方案 5：方案 2 的风险集中在无法控制的外部环节（Orca 启动命令可替换性、包装器协议保真、Codex 用户层 header 配置），且覆盖不了不经包装器启动的会话——包括 /implement-spec 这类 skill 自建的临时 worktree；方案 5 的全部改动落在自有代码 MemoryProxy 内，对其他用户也是正向产品能力（目录即项目、仓库即身份）。不愿改 Proxy 时仍可用方案 2；若 Orca 不能调用包装器，再考虑方案 3（在现有 SessionStart 基础上新增受鉴权注册入口，需验证 session ID 对齐与时序，并与 claude-mem hooks 共存）。依据与约束见研究记录。
